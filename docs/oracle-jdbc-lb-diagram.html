Oracle JDBC · Two-Port Connection Flow

// listener redirect model & load-balancing DNS implications

Connection Architecture Diagram
Connection Steps
  • ① DNS ResolutionClient resolves hostname → single IP (e.g. 10.0.0.1)
  • ② TCP Connect to Port 1521Client opens TCP connection to listener on the well-known port
  • ③ Listener Forks a Server ProcessListener spawns (dedicated) or locates (shared) a server process, which binds to a random ephemeral port
  • ④ Redirect ResponseListener sends back a new address + port (e.g. 10.0.0.1:59821). The original :1521 connection is then closed.
  • ⑤ Second TCP ConnectionClient opens a brand new TCP connection directly to the server process on the dynamic port
  • ⑥ SQL Session ActiveAll SQL traffic flows on this second connection. The listener is no longer involved.
Why LB DNS Breaks This
⚠ Core Problem The redirect response from the listener contains a hostname or IP for the second connection. With plain LB DNS, this address may be:
  • An internal hostname the client can't resolve
  • A node IP bypassing the load balancer
  • Blocked by a firewall that only allows :1521
  • ①② DNS & Initial Connect work fineLB DNS resolves to e.g. 10.0.0.1, client connects to :1521 — no issue yet
  • ③ Redirect contains internal addressListener on 10.0.0.1 responds with node1.internal:52340 — its own hostname, not the LB DNS name
  • ④ Second connection fails or bypasses LBClient must resolve the redirect host. The load balancer is completely bypassed for the actual session.
Solutions
✓ Oracle RAC + SCAN (Recommended) Single Client Access Name (SCAN) is Oracle's purpose-built solution. The SCAN listener routes to node VIPs — addresses that are always stable and routable. No LB DNS games needed.
  • ① Connect to SCAN hostnameSCAN DNS returns up to 3 SCAN VIP addresses. Client picks one and connects on :1521
  • ②③ SCAN listener routes to a nodeInternally load-balanced. Returns a redirect to a Node VIP — a stable, known-routable address
  • ④ Client connects to Node VIP directlyThe Node VIP is always reachable; firewall rules can be set to allow the dynamic port range from the node VIPs
Other Options (single-node)
  • Configure LOCAL_LISTENER to return the LB VIP in redirects
  • Use connection pooling (DRCP / UCP) to avoid per-session redirects
  • Allow dynamic port range in firewall between client and DB host
  • Use SERVER=SHARED with dispatcher — dispatcher port is fixed & configurable
